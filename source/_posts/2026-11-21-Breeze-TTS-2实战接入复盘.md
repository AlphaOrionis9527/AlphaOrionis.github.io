## 一、起因：我想让助手"用自己的声音"说话

做 AI 助手这件事久了，总会遇到一个小小的执念：文字回复再快，也不如一段**听得出同一个人的**语音让人安心。

于是我给自己定了一个目标——用本地模型做语音合成，不依赖任何云端 API，不上传任何文本，声音固定、延迟可控、离线可用。

选型的时候，Breeze-TTS-2（`BreezeBlue/Breeze-TTS-2`）进入了视野。它提供三条能力路径：

1. **Voice Clone（声音克隆）**：给定一段参考音频 + 对应的逐字稿，复刻那个人的音色；
2. **Voice Design（声音设计）**：只给一句风格描述，让模型"画"一个说话人；
3. **Voice Direction（语音导演）**：在克隆或设计的基础上追加情绪、语速、表演风格指令。

它支持中英双语，文本里还能内嵌 `[笑]`、`[叹气]` 这类事件标记。听起来很美好。

然后我花了将近一周，把它接进了 OpenClaw 的回复链路。这篇文章不是产品评测，是**一份事故复盘**：七道坎，每一道都真实地绊倒过我一次。

---

## 二、坎一：许可证比 README 藏得深

在任何一行代码之前，先看两件容易被跳过的事：**代码许可证**和**权重许可证**。

Breeze-TTS-2 的代码部分是 **Apache 2.0**，可以商用；但**模型权重**适用的是另一份协议：

> **BREEZEBLUE RESEARCH AND NON-COMMERCIAL LICENSE AGREEMENT**
> 仅允许研究与非商业用途；商业使用需另行取得书面许可。

这两者常被混为一谈，我也差点混过去。需要特别注意的是：

- 官方提供的**云端付费订阅**，其商业授权并不自动延伸到你本地下载的权重；
- 自己托管权重做商业场景，和调用官方 API 是两件事。

我的场景是个人非商业使用，正好落在允许区间内——但这个结论必须**明确写下来**，而不是默认"开源=随便用"。

> **教训一**：先读 LICENSE，再看 README。README 里那句 "Apache 2.0" 说的是代码，不是模型。

## 三、坎二：模型能跑，但在虚拟机里跑不稳

我的开发环境是一台 Apple Silicon Mac 上的 macOS 虚拟机（Apple Virtualization / Parallels）。为了跑 MLX，我装了：

- `mlx` / `mlx-metal` 0.32.4
- `mlx-audio` 0.6.5
- 模型权重 `mlx-community/Breeze-TTS-2-mlx-4bit`（4bit 量化，MLX 原生社区移植）

一切看起来都很顺——直到我开始合成**长句子**。

现象是灾难性的：

| 输入 | 输出 | 结果 |
|---|---|---|
| 19 字 / 38 token | 3.04s | 健康，波形正常 |
| 40 字 / 110 token | — | 削顶噪声，peak 直接打到 32767 |
| 40 字 / 363 token（循环重复） | 29.04s | 近直流，peak 只有 187，彻底失真 |

更要命的是**连续生成**：同一个进程里第一次合成是好的，第二次开始就出现 Metal 状态累积，音频开始漂移；再往后直接报 `No Metal device available` 或 `METAL_TIMEOUT`。

根因很清楚：虚拟机里的 Metal 是 **paravirtual（半虚拟化）通道**，不是原生 Metal。它在短句、单次调用上能糊弄过去，一旦持续占用或长时间推理，通道就会掉线。

于是我写了第一版对策——**分段生成**：

```python
# 按中文标点切句，每段不超过 22 字（已验证健康上限 19 字 / 38 token，留一点余量）
MAX_CHARS = 22
SEG_TIMEOUT = 25          # 单段硬超时
METAL_WAIT = 120          # Metal 掉线后的恢复等待

# 每段用【全新进程】生成，绝不在同一进程里连续跑
# 生成前先探针确认 Metal 回来了
```

流程变成：**切段 → 等 Metal → 起独立进程生成 → 体检 → 身份核对 → 拼接 → 整体体检**。

这确实让长文本"能出声"了，但只是把一个 bug 换成了另一个 bug——下一道坎更隐蔽。

## 四、坎三：声音会"换人"

第一版分段跑通后，我第一次完整听了一遍输出，汗毛竖起来了。

那是一条回复被切成四段，四段的基频分别是：

> **207.8 Hz / 104.3 Hz / 142.4 Hz / 176.5 Hz**

这不是同一个人在说话。这是**至少三个不同的人**。

原因在于我最初用的是 **Voice Design 路径**：只传 `--voice S7` 加一句 `--instruct`。在这条路径里，S7 只是一个**先验采样种子**，每次独立采样都会各画各的人——分段恰恰放大了这个问题，因为每段都是一次全新的随机采样。

修法是改走 **Voice Clone 路径**，把身份**结构化地锚定**：

```bash
# 每段都带同一份参考音 + 同一份逐字稿
--ref-audio ~/.breeze-ref/S7.wav \
--ref-text  "哥哥，这是 Breeze 二代的中文语音样本。"
```

参考音是固定的（MD5 `e0bf7f7745732f9e11f6766f9000fb70`，24kHz、非静音），逐字稿也是固定的。**"是同一个人"从此由结构保证，不再靠每次采样碰运气。** instruct 依然保留——它管语气和风格，与身份锚点不冲突。

但"结构上保证了"还不够，因为生成模型本身仍可能在小样本上飘。所以下一步是**给声音上体检**。

---

## 五、坎四：怎么判断"这两段是同一个人"

这是整件事里技术上最硬的一段。我的判断标准分三层：

**第一层：基频比值（逐段）**
每一段与参考音的 F0 中位数比值必须落在 `[0.85, 1.15]`。

**第二层：组内基频极差**
同一条回复的所有段之间，两两 F0 比值的最大跨度不得超过 `1.45`。这一条专门抓"某一段突然变成另一个人"。

**第三层：逐帧 MFCC 最近邻（跨说话人判决）**
这一层我推翻重做过一次，过程很值得记下来。

最初的判据是"整句 MFCC 谱形状距离"，阈值 0.34。实测结果是——**判别力为零**：

- 同一个人：27 段，距离落在 `0.0166 – 0.2782`
- 不同的人：4 段，距离落在 `0.0804 – 0.1821`

异人簇**完全落在**同人簇内部，异人样本甚至直接通过了旧门禁；反过来，中英混排的正常同人段却被误杀到 `0.4250 – 0.5492`。这是典型的"**拦错人、放错人**"——门禁看起来在把关，实际上两头都不准。

于是我换了判据：不再比整句，而是**逐帧**算 MFCC（去掉 c0、做 L2 归一化），取每一帧到"同人参考帧池"的**最近邻余弦距离**，再用中位数代表这一段。

帧池用的是生产数据本身：参考音 + 标定集 13 段 + 交付段 14 段，共 28 个确认同人的文件。用**留一法**校准（排除自身路径与自身 MD5，避免自己判自己）：

- 同人上界：`0.0282`
- 异人下界：`0.0743`
- 中间间隙：`0.0461`（相对同人上界 163.3%）
- 阈值取中点：**`0.0513`**

同时保留原来的 F0 两项阈值不变——因为 F0 单独抓不到"F0 比仅 1.141"的异人样本，这最后一刀要由帧最近邻补上。

最终门禁配置长这样：

```json
{
  "nn_outlier_max": 0.0513,
  "f0_ratio_lo": 0.85,
  "f0_ratio_hi": 1.15,
  "pair_f0_spread_max": 1.45,
  "mfcc_outlier_max": 0.34,
  "use_mfcc": false,
  "source": "calib-20261116-v5-framenn"
}
```

注意 `use_mfcc: false`——旧的整句 MFCC 不再承担跨说话人判决，只作为咨询项留着。

**门禁的工程纪律**也有几条铁律：

1. **独立验收**：生成器自己报告"通过"不算数，必须由独立门禁工具复核（逐段 F0、组内 F0 极差、逐帧 MFCC 最近邻三项齐查）；
2. **格式硬约束**：门禁候选音频必须保持 `24 kHz / Int16 / 单声道`；AIFF 必须先转成 RIFF/WAV 再进判定；
3. **解释器锁定**：语音门禁必须用 `~/.breeze-venv/bin/python`，系统 `python3` 没有 `scipy`；
4. **失败即失败**：某段不合格就换 seed 重生成，连续不合格则整链判失败，绝不把"混人"的音频当交付。

## 六、坎五：最危险的一次事故——静默回退

到这里链路已经能稳定产出"同一个人的声音"了。然后我做了一件**自作聪明**的事：加了个兜底。

逻辑是这样的：Breeze 失败时，如果不发声，多半会被用户投诉；那就 fallback 到系统自带的 `say` 语音吧，至少有声音。

于是发生了这样一幕：某次回复里，Breeze 悄悄失败了，系统用系统语音（Meijia）补上，而**用户听到的是"突然换了个人"**。

这就是那个"偶尔换了个人"的真相。

更糟的是它**静默**：失败被掩盖了，看起来像模型不稳定，实际上是我的容错策略在偷偷换嗓子。

修法只有一条：**删掉自动回退**。

```bash
# 现在的语义：默认 breeze，失败就是失败
MAGGIE_VOICE=breeze|say     # 默认 breeze
# say 只保留为【显式手动】应急路径：
#   - 产物文件名强制带 -meijia 后缀
#   - provenance 标注 voice=say-meijia
#   - 永远不会被误当成 S7 交付
```

> **教训五**：**降级不等于容错。** 一个会骗过用户、也会骗过你自己的降级路径，比一次响亮的失败糟糕得多。宁可让链路安静地失败，也不要让错误悄悄通过。

## 七、坎六：声音对了，却只播了三秒

新问题：语音文件生成正确，但播放总在开头就断。

原因在进程模型：`OpenClaw` 的执行环境在工具调用结束时会**按 process-group 收割子进程**，所以最常见的写法

```bash
( afplay "$AUDIO" & )
```

会在工具调用结束时被连带杀掉。实测：调用内 3 秒音频还活着，下一次工具调用时进程已经没了——声音自然只播了开头。

解法是**双 fork + `POSIX::setsid()`**：写了一个小工具 `state/detach-exec.pl`，把 `afplay` 扔出当前进程组，让它 reparent 到 `launchd`（ppid=1），跨工具调用存活，完整播完。

从此正式入口固定为一个脚本：

```bash
sh ~/.openclaw/workspace/Tools/voice.sh <tag> /tmp/voice-reply.txt
# stdout: AUDIO=<path> / SIZE=<bytes> / PLAYING=yes
# stderr: VOICE=breeze-s7
```

所有语音都从这里走，**不再有第二个 `afplay`**。

## 八、坎七：把合成搬到宿主真机

前面所有的分段、探针、等待 Metal，都是在跟虚拟机的半虚拟化 Metal 较劲。这些补丁治的是症状。

真正的解法是：**让合成这一步跑在原生 Metal 上**。

于是我把服务拆成了两半：

- **宿主真机**（原生 Apple Silicon，arm64，Python 3.12.9）跑 `Tools/breeze-host-service.py`，常驻模型权重，负责真正"发声"；
- **客机虚拟机**负责切段、调度、身份门禁、拼接和播放。

宿主服务对外暴露三个接口：

```
GET  /health          -> {"ok":true,"ref_ready":true,"ref_md5":"...","metal":true,...}
GET  /v1/models       -> OpenAI 兼容的模型列表
POST /v1/audio/speech -> {"input":"...","voice":"S7"}  -> 24kHz 单声道 16bit WAV
POST /upload/ref      -> 上传/更新参考音
```

服务端的纪律写死在代码里：

1. **一次只跑一个 MLX 任务**（全局锁），绝不并行抢占 Metal；
2. **参考音缺失就拒绝合成**（返回 503），绝不用别的嗓子顶替；
3. **服务端不吞异常**，失败即 5xx + 原因；
4. 两种模式可切：`BREEZE_ONESHOT=0`（模型常驻，快）/ `=1`（一请求一进程，慢但彻底规避状态累积）。

切换是**文件驱动**的，不需要重启 Gateway：

```bash
# state/breeze-host.env 存在 = 合成跑在宿主真机
MAGGIE_BREEZE_HOST=http://<host-ip>:8000
MAGGIE_BREEZE_HOST_TIMEOUT=180
# 删除这个文件 = 回滚到本机路径
```

回滚路径从头到尾完整保留——这在生产系统里比"跑得漂亮"重要得多。

## 九、接入 OpenClaw：最终生产链路

OpenClaw 的 TTS provider 指向本地 CLI：

```json
{
  "provider": "tts-local-cli",
  "auto": "off",
  "providers": {
    "tts-local-cli": {
      "command": "~/.openclaw/workspace/Tools/breeze-tts-cli.sh",
      "args": ["-o", "{{OutputPath}}"],
      "outputFormat": "wav",
      "timeoutMs": 300000
    }
  }
}
```

完整链路一图流：

```text
回复文本
  → 按标点切段（每段 ≤ 22 字）
  → 逐段提交宿主 /v1/audio/speech（clone：固定参考音 + 固定逐字稿）
  → 每段独立健康检查（采样率 / 通道 / 位深 / 峰值 / 时长）
  → 逐段身份门禁（逐帧 MFCC 最近邻 + 逐段 F0 + 组内 F0 极差）
     └─ 不合格 → 换 seed 重生成 → 连续不合格 → 整链失败（exit 4）
  → 拼接为 24kHz 单声道 WAV
  → detach-exec.pl 双 fork 播放（绕过 process-group 收割）
  → 交付：S7 的声音，全程同一个身份
```

几点补充：

- `tts.auto` 全局关闭，语音只在我**显式请求**时生成，不做无意义的自动播报；
- 保留了一份 OpenAI-compatible 的备用配置（指向本机 `mlx-community/Breeze-TTS-2-mlx-4bit`，声线 `S7`），作为宿主不可用时的应急形态；
- 超时上限给到 300s——因为首段要现加载模型权重，远程模式的分段预算按 `段数 × (35s + 8s)` 计算。

## 十、复盘：七道坎与它们各自的解法

| # | 现象 | 根因 | 解法 |
|---|---|---|---|
| 1 | 以为可以随便商用 | 只看了 README 的 Apache 2.0 | 读权重协议：研究 + 非商业 |
| 2 | 长文本削顶 / 近直流 / 连续生成掉线 | 虚拟机 paravirtual Metal 不稳定 | 分段（≤22 字）+ 独立进程 + Metal 探针 + 恢复等待 |
| 3 | 一条回复里像换了三个人 | Voice Design 路径每段独立采样 | 改走 Voice Clone，固定参考音 + 固定逐字稿 |
| 4 | 门禁"拦错人、放错人" | 整句 MFCC 判别力实测为 0 | 改逐帧 MFCC 最近邻 + 留一法校准，阈值 0.0513 |
| 5 | 偶尔"换了个人" | 静默回退到系统语音 | 删除自动回退，失败即显式失败 |
| 6 | 语音只播开头三秒 | process-group 收割后台 afplay | 双 fork + setsid 脱离进程组 |
| 7 | 补丁越堆越多仍不稳 | 在错误的地方治症状 | 合成迁移到宿主真机原生 Metal，客机只做编排与验收 |

如果让我浓缩成三句话：

1. **"能出声"离"像个人"还很远。** 语音合成的难点从来不是音质，而是**一致性**。
2. **门禁的判据必须用真实分布校准，不能凭感觉设阈值。** 我那个 0.34 的旧阈值看起来很合理，实测判别力是 0。
3. **失败要响亮。** 任何"悄悄替换结果"的降级路径，最终都会变成最难查的 bug。

---

## 十一、结语

现在，我的助手每一条语音回复都来自同一段固定的参考音，经过三道独立的身份核对，落在同一块原生 Metal 上。

这件事最有意思的地方不是模型本身，而是它逼着我把"一致性"当成一等公民——在文字生成上我们几乎从不担心"这会儿是不是换了个人"，但在声音上我们必须担心，因为耳朵比眼睛诚实得多。

也许这就是为什么做语音比做文本更难，也更有意思。
